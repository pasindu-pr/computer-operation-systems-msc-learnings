Module 1

⚡ Low-Level Hardware Support for the OS

An operating system cannot protect the computer by software alone. The hardware must help it. In this module you will see how interrupts return control to the OS, CPU modes restrict dangerous instructions, and hardware protects memory, processor time and I/O.

1 Interrupt-Driven Operation

Simple idea: a device tells the CPU when it needs attention, so the CPU does not have to keep checking it.

In simple words: the CPU can work on a program while a disk, keyboard or network device works at the same time. This is called concurrent operation.

When a device finishes or needs service, it sends an interrupt. The CPU pauses its current program, runs the operating-system code that handles the event, and can then continue. Without interrupts, the CPU would waste time repeatedly asking, “Are you finished yet?”

  • Each I/O device type has a device controller that controls that device.
  • Each controller has a local buffer (small on-board memory).
  • Real I/O happens between the device ⇄ its local buffer. The CPU then moves data between main memory ⇄ local buffer.
  • When the controller finishes, it raises an interrupt to tell the CPU.
🍽️ Real-world analogy — The restaurant kitchen You are the chef (CPU). You start the toaster (device) and chop vegetables while it works. Its “ding” is the interrupt. You pause, deal with the toast, and continue chopping. The important point is not that both jobs use the CPU; it is that the device works independently and only signals the CPU when service is needed.

To identify which interrupt happened, the OS uses one of two methods:

MethodHow it works
PollingOS checks each device controller's status register one by one to see if it needs service. Simple, but wastes time asking everyone.
Interrupt vectorsUses a table of addresses (“vectors”) of Interrupt Service Routines. The interrupt passes a number = an index into the table → jumps straight to the right ISR. Fast.
  • The ISR (Interrupt Service Routine) is part of the OS and carries out the right action for that interrupt type.
  • When the ISR finishes, the OS either restores the interrupted program's saved registers, or calls the scheduler to decide if a different program should run next.
  • In the simple scheme used in the lecture, new interrupts are masked while one is being processed so the current interrupt is handled safely and another is not lost.
  • Real systems can use interrupt priorities: a higher-priority interrupt may interrupt a lower-priority ISR, while equal or lower priorities remain masked.

Two families of interrupt

🔌 Hardware interrupt Comes from outside the running program:
  • An I/O device signalling completion
  • A hardware fault (e.g. “power low” on a laptop)
💻 Software interrupt (a “trap”) Generated by the running program itself:
  • A program deliberately asking the OS for a service (this is how system calls work!)
  • A software error, e.g. divide by zero
Q A program executes x = 5 / 0. What kind of interrupt is generated?
A hardware interrupt from the CPU's cooling fan
A trap (software interrupt) caused by a software error
No interrupt — the program just returns 0
✅ A trap. A software error like divide-by-zero is a software-generated interrupt (trap). The CPU traps into the OS, which decides how to deal with the faulting program.

2 CPU Dual-Mode Operation

Simple idea: ordinary programs receive limited CPU permissions; the OS receives full permissions.

Your browser, editor and music player share the computer. If any one of them could directly control devices, change protection registers or stop another process, one bug could damage the whole system. The CPU therefore provides at least two execution modes:

ModeWho runs herePowers
User mode (bit = 1)User programsOnly a subset of the instruction set is allowed
Supervisor mode (bit = 0)
a.k.a. monitor / system / kernel mode		The operating systemCan execute all instructions, including privileged ones
  • A mode bit in hardware records the current mode (0 = supervisor, 1 = user).
  • Privileged instructions can only run in supervisor mode (e.g. “kill a running program”, load base/limit registers, do I/O, load the timer). Changing the mode bit is itself privileged.
  • How the switch happens: when an interrupt/fault occurs → hardware switches to supervisor mode. When the OS restarts a user program → switches back to user mode.
  • Key guarantee in this lecture model: an interrupt, exception or system call transfers control through a protected entry point into OS code and changes the mode to supervisor. A protected return changes it back to user mode. A user program cannot set the mode bit itself.
🏨 Real-world analogy — The hotel keycard A guest keycard (user mode) opens only permitted doors. A staff master key (supervisor mode) opens protected areas. A guest cannot turn their card into a master key; they must ask the front desk through a controlled request. In the same way, a program asks the OS through a system call instead of running a privileged instruction itself.

⚠️ Why memory protection becomes necessary If a user program could overwrite an interrupt-vector entry or an ISR, the CPU might enter supervisor mode and jump into attacker-controlled code. The vector table and kernel code must therefore be stored in memory that user mode cannot modify.

3 Memory Protection — Base & Limit Registers

Simple idea: hardware checks every user-mode memory address before allowing the access.

In simple words: each process is given an allowed stretch of physical memory. Two protected registers describe that stretch:

  • Base register — holds the smallest legal physical address the program may touch.
  • Limit register — holds the size (range) of the allowed region.

For the lecture's physical-address check, an access is legal only when base ≤ address < base + limit. Example: base = 300,000 and limit = 120,000 allow addresses 300,000 through 419,999; address 420,000 is outside the region. An illegal access causes a protection exception/trap to the OS. Only the OS can load these registers, and supervisor-mode OS code can access all memory.

4 CPU Protection — The Timer

In simple words: the OS sets an alarm before giving the CPU to a program. Even if that program enters an infinite loop, the alarm returns control to the OS.

  • The timer interrupts the computer after a set time elapses, guaranteeing the OS gets control back.
  • It is decremented every clock tick; when it hits 0, an interrupt occurs.
  • Used to implement time-sharing (slicing CPU time between programs) and to compute the current time.
  • Loading or disabling the timer is a privileged instruction, so a user process cannot prevent the OS from regaining control.
⏲️ Real-world analogy — The debate moderator's buzzer Each speaker (program) gets a time slot. The moderator (OS) sets a buzzer (timer) before handing over the microphone. When it rings, the moderator regains control and may choose the next speaker. Loading the timer is privileged, so a speaker cannot secretly give themselves unlimited time.

5 Synchronous vs Asynchronous I/O

🔒 Synchronous I/O

The requesting program continues past the I/O operation only after the operation completes.

  • CPU waits — either goes idle until the next interrupt, or sits in a busy loop polling the device.
  • At most one I/O request outstanding at a time. No overlap.

⚡ Asynchronous I/O

The request is started and control returns without waiting for completion. The device and CPU can then work concurrently.

  • Needs a device-status table — one entry per device with its type, address and state.
  • Multiple requests can be queued (linked list) per device.
  • OS indexes into the table to check each device's status.
☕ Real-world analogy — Ordering coffee Synchronous: you order and wait until the drink is ready before continuing. Asynchronous: you receive a buzzer, do something else, and return when it rings. The buzzer is like a completion interrupt. The exact theory is about when control returns to the requester, not simply whether the physical CPU is idle.

6 I/O Protection & System Calls

All I/O instructions are privileged — so a user program can't directly grab a device and mess with another program's data. But then… how does a user program do I/O at all?

It uses a system call: a controlled request to the kernel, such as creating a process, opening a file or reading from a device. A system call is the service interface between a running process and the OS.

How a system call actually works

The program passes information about the exact service it wants via parameters. The OS verifies those parameters are correct and legal, executes the request, and returns control.

Passing data to the OS — two schemes

📨 Message passing — hand the OS a message/block of parameters
🧠 Shared memory — put params in a memory region both can read
Q Why are all I/O instructions made privileged?

✅ Privileged I/O prevents one program reading/writing another's data. Programs must instead ask the OS via a system call, which checks the request is legal first.

7 Direct Memory Access (DMA)

Direct Memory Access (DMA) lets a DMA-capable controller transfer a block between an I/O device and main memory. The CPU sets up the transfer, continues other work, and is normally interrupted when the block is complete.

  • Used for high-speed devices that transmit near memory speed.
  • The controller transfers whole blocks straight to memory using cycle stealing (borrowing memory-bus cycles).
  • Only one interrupt per block — instead of one interrupt per byte. Huge CPU saving.
🚚 Real-world analogy — Bulk delivery vs one parcel at a time Think of the CPU as a manager and the DMA controller as a delivery team. The manager gives the team the pickup point, destination and block size. The team moves the block and reports once at the end. The CPU is still involved in setting up and completing the operation, but it does not copy every byte itself.

8 Memory Structure, Hierarchy & Caching

Main memory (RAM) The only large area the CPU can access directly. It is volatile (lost on power off) and not big enough to hold everything.
Secondary memory An extension of main memory — large, non-volatile storage: HDD, SSD, CD/DVD, USB.

Storage is organised in a hierarchy: as you go up, you get more speed but higher cost per byte, smaller size, and more volatility.

The Caching Principle

Caching means keeping a copy of likely-needed data in faster storage. On a hit, the fast copy is used; on a miss, data is fetched from the slower level and may be copied into the cache. In the storage hierarchy, RAM can be viewed as a cache for secondary storage.

The core challenge of caching You must maintain a mapping between the copy and the original, and keep them consistent (if you change the copy, the original must eventually match). Example: a disk cache (e.g. 64 MB) sits between the slow disk and the faster microprocessor, holding recently used clusters.

Module 2

🪟 Overview of Windows Operating Systems

This module follows the lecture's historical view of Windows, then explains the Windows NT design from bottom to top: hardware, HAL, drivers, kernel, Executive, system libraries, services and applications.

1 The Evolution of Windows

Big picture: Microsoft once maintained two Windows families. The consumer family kept compatibility with MS-DOS; the NT family was a newer design focused on reliability and security. Windows 2000 brought NT to the business desktop, and Windows XP later placed both consumer and business editions on the NT code base.

🏠 Domestic / consumer line Windows 95, 98, ME — still built on legacy MS-DOS code (DOS handled things like the file system), so old code ran slower and these were often unstable.
🏢 Corporate / business line Windows NT 3.1, 3.51, 4.0 — “New Technology”, written from scratch in newer 32-bit code (a joint venture with IBM, similar to OS/2). Emphasis on security & reliability over UI polish and gaming.

Early versions & the DOS front-end

Windows 1.0 / 2.0 / 3.0 / 3.1 were essentially a GUI front-end on top of the command-line MS-DOS. Windows 95 added 32-bit apps, Plug & Play, virtual memory, multitasking and long filenames — but was still DOS-based underneath.

2000 → XP → Vista → 7 → 8 → 10: Windows 2000 was NT 5.0; XP was NT 5.1 and completed the move of mainstream consumer Windows to the NT family; Vista was NT 6.0; Windows 7 refined Vista's NT 6.x base; Windows 8 introduced a touch-focused interface for PCs and tablets; and the lecture highlights Cortana and HoloLens in the Windows 10 period.

4 Windows NT Internal Architecture

Start with the simple idea: Windows NT is not explained well by one architecture label. It combines ideas from the monolithic, layered/modular and client/server models.

  • Layered portion: Hardware Abstraction Layer (HAL) → Device drivers & Kernel → NT Executive.
  • Client/server portion: the subsystems and Windows services that user programs call.
  • Core components use object-based and modular design principles: components have clear responsibilities and communicate through defined interfaces. Much of NT was implemented in C, but its internal object model still provides encapsulated OS objects.

5 Inside the NT Executive

The NT Executive is a collection of mostly hardware-independent kernel-mode managers. Each manager has a focused job and uses defined interfaces to work with the others. User-mode environment subsystems reach native system services through routines in ntdll.dll.

The bottom & top of the stack

  • HAL (Hardware Abstraction Layer): low-level interface that hides hardware-specific details, giving other OS parts a common way to access hardware. The right HAL is chosen at install time.
  • Device drivers: kernel software for devices and software devices such as file-system and network drivers. Hardware drivers use Windows kernel and HAL interfaces to deal with platform-specific hardware details.
  • Kernel (Ntoskrnl.exe): gives other components a common set of processor services regardless of CPU architecture. Handles thread scheduling, synchronisation, interrupt/exception handling, context switching, and manages kernel objects.
  • Subsystems & services (user mode): environmental subsystems let programs written for other OSes run on Windows; support processes provide logon, spooling, etc. — organised client/server.
  • NTDLL: a user-mode system library containing the native API and low-level system-call entry routines used by Windows subsystems. A .dll is a dynamic-link library: code and data that programs can load and reuse.
Q A component needs to talk to a brand-new type of graphics card. In Windows NT's design, it accesses the hardware through…
The Hardware Abstraction Layer (HAL)
Directly poking the hardware ports itself
The Configuration Manager's Registry
✅ The HAL hides hardware specifics behind a common interface — this is what makes Windows portable to different hardware. Drivers and internal components go through the HAL rather than touching hardware directly.
Module 3

🐧 Linux Shells & Bash Scripting

A shell reads commands and asks the operating system to perform them. This module keeps the full command-line theory, but explains each symbol by following where its input and output go.

1 What is a Shell?

A shell is a command interpreter. It reads what you type, expands shell syntax such as variables and wildcards, runs built-in commands or starts programs, and reports their output and exit status. Those programs use system calls to request services from the kernel.

ShellCharacter
sh (Bourne)The original UNIX shell. Small, basic, few features.
bash (Bourne Again)The GNU shell commonly used as the interactive default on Linux. It is largely compatible with Bourne/POSIX shell syntax and adds features of its own; a Bash-specific script may not run under plain sh.
csh (C shell)Syntax resembles the C language. Added the useful history feature and job control.
tcsh (Turbo C)A superset of csh — more user-friendly and faster.
ksh (Korn)A superset of the Bourne shell, liked by people with a UNIX background.

Linux uses a broad file-like interface: ordinary files, devices, pipes and many kernel interfaces can be opened, read or written in similar ways. The approved login shells are commonly listed in /etc/shells. echo $SHELL shows your configured login shell; it may not identify a different shell started inside the current session.

2 The Two Superpowers: Piping & Redirection

| Piping

Connects the first command's standard output to the next command's standard input. Each command can do one small job, and the pipeline combines them.

command1 | command2 | command3

> Redirection

Changes where a command reads input or writes output. > writes standard output to a file and replaces that file's old contents; >> appends instead.

ls -R / | grep httpd.conf > results.txt
🏭 Real-world analogy — A factory assembly line A pipe | is the conveyor belt: the half-built product from station 1 rolls straight into station 2. Redirection > is the packing box at the end — instead of the product coming out to you (the screen), it gets boxed and stored (a file). Example: ls -R lists the whole filesystem; the belt sends it into grep which filters for one filename; > boxes the survivors into a file.

Control operators (combine commands)

;semicolonRun commands in sequence, whether the previous command succeeds or fails
&&andRun 2nd command only if the 1st succeeds

Handy extras: Tab = auto-completion. history = every command is logged (via the HISTFILE variable, e.g. .bash_history). Arithmetic: ((expr)). File/string tests: [[ expr ]]. Predefined variables include PWD, OLDPWD, PATH, HISTFILE, HISTSIZE, EDITOR, SECONDS.

5 Writing Scripts

A shell script is a text file containing commands. The shell reads them in order, using the same syntax you use interactively. You can run it explicitly with bash scriptname, or make it executable and run it as a program.

#!/bin/bash # the "shebang": tells the shell to use /bin/bash # My first script # everything after # is a comment (ignored) echo "Hello World!" # prints to the screen
  • Line 1 — the shebang #!/bin/bash tells the shell which interpreter to use (perl, python, etc. use the same trick).
  • Comments start with # and are vital as scripts grow.
  • Make it executable with chmod u+x first_script. The execute bit is what matters; terminal colours vary by theme and are not part of the permission model.
  • Run it from the current directory with ./first_script. The ./ is needed when the current directory is not in PATH.
🔑 The passwd file format A recurring exam favourite. Each line of /etc/passwd is:
username:password:UID:GID:GECOS:home_directory:shell
So cut -d: -f1 /etc/passwd grabs field 1 (the username), using : as the delimiter. Pipe it into | sort to alphabetise.

Module 4

🧠 Virtual Memory

Virtual memory gives each process a large logical address space even when RAM is limited. The OS and hardware keep the currently useful pages in RAM and store other pages in secondary storage until they are needed.

1 Why We Need Virtual Memory

Problem: RAM is limited. If the OS and active processes need 5.5 GB but the machine has only 4 GB of RAM, keeping every byte of every process in RAM at once is impossible.

  • The Long-Term Scheduler could just refuse to admit new processes until others finish and free memory — but that's restrictive.
  • Virtual memory allows only part of each process to be resident in RAM. Other parts remain in a disk-backed store until needed. Therefore the total virtual memory in use can exceed physical RAM, although heavy disk access makes the system much slower.
  • The allocation scheme decides which parts live in RAM. General idea: keep the data/instructions that are being used now or likely to be used soon. This is implemented via demand paging (or demand segmentation).
Logical address space can be > physicalMore processes can run at onceA process can be bigger than RAM
🍳 Real-world analogy — The tiny kitchen counter Your kitchen counter is RAM; the pantry is secondary storage. Ingredients for the current step stay on the counter. If the next ingredient is in the pantry, you pause to fetch it: that delay is like a page fault. If the counter is full, you first move something back: that is page replacement. The analogy explains capacity, but remember that disk is vastly slower than RAM.

2 Demand Paging & Page Faults

Demand paging loads a page into a free physical frame only when the process actually references it. This avoids loading pages that may never be used.

  • In the lecture's demand-paging model, each page-table entry has a valid/invalid (resident) bit: 1 means the page is currently in memory; 0 means it is not resident. At process start, none of its pages may be resident.
  • When a process references a page whose bit is 0, a page fault is generated — an interrupt telling the OS the referenced page isn't in memory.
  • The OS must distinguish two cases: the address may be outside the process's legal address space, which is an error, or it may be legal but its page is not currently in RAM, which can be serviced. Real page tables commonly use separate protection and presence information even when teaching diagrams combine them.

Servicing a page fault

Page fault
→
Find a free frame (or a victim)
→
Swap the page in from disk
→
Update page table + PCB (valid = 1)
→
Restart the instruction

With pure demand paging and no pre-paging, the first reference to a page that is not resident causes a page fault. If the OS preloads a page, its first reference can be a hit.

3 Performance: Effective Access Time (EAT)

A page fault is expensive because the OS must trap into the kernel, validate the address, find or free a frame, perform disk I/O, update tables and restart the instruction. Effective Access Time (EAT) is the weighted average of normal accesses and faulting accesses.

Let p = page-fault rate (0 ≤ p ≤ 1). If p = 0, no faults; if p = 1, every reference faults.

EAT = (1 − p) × memory access time + p × (page-fault service time)

Worked example from the slides: memory access = 100 ns, page-fault service time = 10 ms = 10,000,000 ns, and p = 0.5. This deliberately huge 50% fault rate shows why faults dominate:

EAT = (1−0.5)×100 + 0.5×(10,000,000 + 100) = 50 + 5,000,050 = 5,000,100 ns ← ~50,000× slower than the 100 ns RAM!

The lesson: the page-fault rate has a huge effect because disk service is millions of nanoseconds slower than a RAM access.

4 Page-Replacement Algorithms ⭐

The heart of the module and your exam. When RAM is full and a new page is needed, which page do we evict?

A reference string records the page number used by each memory reference. Starting with empty frames, simulate an algorithm from left to right and count every reference to a non-resident page as a page fault. For the same string and frame count, fewer faults means better replacement performance.

AlgorithmRuleNote
FIFOEvict the page that has been in memory longest (first in, first out)Simple, but can suffer Belady's Anomaly: more frames can cause more faults!
Optimal (OPT)Evict the page that won't be used for the longest time in the futureGives the fewest possible faults — but needs to see the future, so it's only a theoretical benchmark.
LRUEvict the page whose most recent use is furthest in the pastUses past behaviour as a prediction of future locality. Exact LRU can use timestamps/counters or a stack, although real systems often use cheaper approximations.

5 Frame Allocation, Locality & Thrashing

Allocating frames to processes

  • Equal allocation: every process gets an equal share. 100 frames, 5 processes → 20 each.
  • Proportional allocation: by process size. 100 frames with P1=400K, P2=200K, P3=200K → 50 / 25 / 25.

Global vs local replacement

  • Global: can steal a frame from any process (even a different one).
  • Local: can only replace among the faulting process's own frames.

The Locality Model

Over any period, a process tends to reference a stable set of pages — a locality. Later it shifts to a new locality; localities can overlap (some pages used throughout).

Thrashing

Thrashing occurs when processes do not have enough frames for their current localities. They fault repeatedly, the paging disk becomes busy, and the CPU waits instead of doing useful work. A common condition is: the sum of all active locality sizes is greater than available physical frames.

📚 Real-world analogy — Studying at a cramped desk Your desk (RAM) fits 3 books. While studying one chapter (a locality) you keep pulling 3 related books. If your desk only fits 1 book but you constantly need 3, you spend all your time walking to the shelf and back (swapping) and almost none actually reading. That's thrashing: maximum effort, near-zero progress.

6 Windows & Linux Virtual Memory + Multi-Level Page Tables

The lecture uses a classic 32-bit, 4 KB-page model for Windows and Linux. A 32-bit process can describe 4 GB of virtual addresses, and the address is translated through a two-level page-table structure. This is the teaching model; modern 64-bit systems use larger, deeper structures and do not give every process exactly this layout.

Why multi-level? (the key exam reason)

A flat table needs 1,048,576 entries: 4 GB ÷ 4 KB. At 4 bytes per entry, that is 4 MB per process. A multi-level design breaks the table into page-sized pieces, lets non-adjacent pieces live in memory, and allows unused regions of the virtual address space to have no lower-level table at all.

32-bit logical address: ┌───────────┬───────────┬──────────────┐ │ 10 bits │ 10 bits │ 12 bits │ │ Page Dir │ Page Tbl │ Offset │ │ (1024 PDE)│ (1024 PTE)│ (4K page) │ └───────────┴───────────┴──────────────┘
  • Top 10 bits → index into the Page Directory (1024 Page Directory Entries). Each PDE points to a page table.
  • Next 10 bits → index into the Page Table (1024 Page Table Entries). Each PTE is 4 bytes / 32 bits, holds a 20-bit frame address, and points to a physical frame.
  • Bottom 12 bits → the offset within the 4 KB frame.
  • Final physical address = 20-bit frame address concatenated with the 12-bit offset. Associative registers cache recent PTEs. Each page table / directory fits in a single 4K page.
  • Linux works the same way: top 20 bits = page number (via multi-level table), bottom 12 bits = offset.

7 Demand Segmentation

Demand segmentation is the segment-based counterpart of demand paging and was used on systems without suitable paging support. The lecture's OS/2 example tracks each segment with a descriptor and valid bit. A reference to a non-resident segment causes a segment fault; the OS loads the segment and restarts the instruction.

1 Address Binding

2 Logical vs Physical Address & the MMU

Logical (virtual) address The address generated by the process.
Physical address The actual location in the memory chips that holds the data.

The Memory-Management Unit (MMU) is hardware that translates logical → physical before the address reaches memory. A simple MMU just adds a relocation register to every address the process generates.

  • With compile/load-time binding, the address used by the running instruction is already an absolute physical address in this simple model. With run-time binding, the program issues a logical address and the MMU translates it.
  • The old “base register” is now called the relocation register.

3 Contiguous Allocation

Contiguous allocation puts all of one process in one unbroken physical-memory region. In the lecture model, the resident OS occupies low memory and user processes occupy higher memory. The limit checks that logical address < limit; the MMU then adds the relocation value.

  • Single-partition: one process at a time.
  • Multiple-partition: several processes, one partition each. Free blocks between them are called holes, scattered at various sizes throughout memory. When a process arrives, the OS finds a hole big enough; it tracks allocated and free partitions.

4 Fragmentation

External fragmentation

Enough total free memory for a process, but it's not contiguous — scattered in small holes outside the partitions. Fix: compaction — shuffle everything together into one big free block (like defragmenting an HDD). Only possible if relocation is dynamic / execution-time.

Internal fragmentation

Memory given to a process is slightly larger than requested; the unused slack sits inside the partition. Happens in paging when the last page isn't full.

5 Paging

Paging removes the need for one large physical block. Logical memory is divided into equal-sized pages; physical memory is divided into equal-sized frames. Any page can occupy any free frame, and the page table records the mapping.

Worked example Process = 108 KB and page size = 10 KB. Ten pages hold 100 KB, so an eleventh page is needed for the remaining 8 KB. Its 2 KB unused part is internal fragmentation. For one process, the maximum waste in its last page is just under one page; if process sizes are random, the average is about half a page.

Address translation

The CPU's address splits into page number (p) + page offset (d). p indexes the page table to get the frame's base address; d is added to give the physical address. Paging eliminates external fragmentation but internal fragmentation can remain. There is a separate page table per process.

Page table implementation & the TLB

  • The page table can live in main memory. The PTBR (page-table base register) points to it, and the PTLR (page-table length register) records its size.
  • Problem: every access then needs two memory accesses — one to read the page table, one for the data. Slow!
  • Solution: the TLB (Translation Look-aside Buffer) — special fast associative registers that allow a parallel search and cache recent page→frame entries.
  • Hit: page number found in TLB → read frame directly. Miss: fetch from the page table in memory and add it to the TLB.

Paging EAT with a TLB

Let α = hit ratio, Ta = TLB lookup time, Tm = memory access time.

EAT = α(Ta + Tm) + (1 − α)(Ta + 2Tm) = Ta + 2Tm − α·Tm

Slide example: α = 0.8, Ta = 20 ns, Tm = 100 ns → EAT = 20 + 200 − 0.8×100 = 140 ns. (Hit path = 120 ns, miss path = 220 ns.)

Paging — memory protection

  • For address-space protection, a valid/invalid bit can say whether the page belongs to the process's legal logical address space. This is conceptually different from the resident/present bit used to say whether a legal page is currently in RAM.
  • A protection bit per entry specifies whether the frame is read/write or read-only.

6 Segmentation

Segmentation follows the programmer's logical view. A program becomes variable-sized segments such as main code, a function group, global data, an array, a stack or an object. Unlike pages, these units have meaning and do not all have the same size.

Pages vs Segments Pages are all the same size; segments vary in size. Because segments vary, allocating them is a dynamic storage-allocation problem (first/best/worst-fit again).

Segmentation architecture

A logical address is a pair <segment-number, offset>. The segment number indexes the segment table (one per process). Each entry has:

  • base — the starting physical address of the segment.
  • limit — the length of the segment. Offset is legal only if offset < limit.

The STBR (segment-table base register) points to the table; the STLR (length register) gives the number of segments — segment number s is legal if s < STLR. Each entry also has a validation bit and read/write/execute privilege bits.

Q Paging suffers internal fragmentation but eliminates external fragmentation. Why no external fragmentation?
Because any page can go in any free frame — physical memory need not be contiguous
Because pages are variable-sized and always fit perfectly
Because the TLB compacts memory automatically
✅ Frames are fixed-size and interchangeable, so the OS can scatter a process's pages into any free frames — no need for one big contiguous block, so no external fragmentation. Internal fragmentation remains because the last page is usually not completely full.

2 Theory Coverage Check

Short, plain-language answers to the remaining ideas asked across both tutorial sheets.

Memory-management comparisons

  • Compile-time vs link/load-time binding: compile-time binding needs the final location early and produces absolute code; link/load-time binding keeps addresses relocatable until modules are combined or loaded. If an absolute location changes, code must be rebuilt or relocated; relocatable code can be placed at a chosen base.
  • Contiguous allocation vs paging: contiguous allocation needs one large hole and uses base/limit translation; paging accepts scattered frames and uses a page table. Contiguous allocation suffers external fragmentation and may need compaction; paging removes external fragmentation but adds page-table overhead and can waste space inside the final page.
  • Internal vs external fragmentation: internal waste is inside an allocated block; external waste is free space split into separate holes. Paging mainly has internal fragmentation. Variable-size contiguous allocation and segmentation can have external fragmentation.
  • Swapping: the OS temporarily moves process memory between RAM and disk-backed swap space. It can let a 384 MB application run on a 256 MB machine if the OS supports virtual memory and the process's actively needed working set fits often enough, but performance may be poor.
  • How paging protects memory: the current process can translate only through page-table entries installed by the OS, and protection bits control read/write/execute access. The OS may deliberately map a shared page into more than one process when controlled sharing is required.

Virtual-memory decisions

  • Why Optimal cannot be implemented exactly: it needs the future reference string. LRU uses the recent past as a prediction; exact LRU has tracking overhead and real systems may approximate it.
  • High paging-disk use + low CPU use: this strongly suggests thrashing. Helpful actions include reducing multiprogramming, adding RAM, and sometimes improving paging I/O. A faster CPU does not fix the missing-frame problem.
  • Pre-paging: loading predicted pages before they fault can help when the prediction is good, but wastes I/O and frames when it is wrong.
  • Larger pages: reduce page-table entries and can improve sequential I/O, but may increase internal fragmentation and load unused data. It is not a guaranteed cure for thrashing.
  • Global vs local replacement: global replacement may take a frame from any process and can improve overall throughput, but one process can harm another. Local replacement chooses only from the faulting process's frames, giving stronger isolation but less flexibility.
